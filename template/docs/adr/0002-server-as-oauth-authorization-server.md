# ADR 0002 — The server is its own OAuth 2.1 Authorization Server

- Status: accepted
- Date: inherited from the template

## Context

Remote MCP clients (claude.ai, Claude Desktop, Claude Code) expect OAuth 2.1 with
discovery (RFC 9728/8414), Dynamic Client Registration (RFC 7591) and PKCE. Upstream
providers rarely offer that directly, and we need one stable tenant per upstream account.

## Decision

- We are the AS: `/.well-known/oauth-protected-resource`,
  `/.well-known/oauth-authorization-server`, `/.well-known/jwks.json`, `/register`,
  `/authorize`, `/token`.
- The login is **upstream-native**: `/authorize` hands the browser to the provider
  (refined by ADR 0007: our own per-client consent screen comes first); `/oauth/callback`
  exchanges the code, identifies the account, stores the encrypted upstream token and
  issues our own authorization code (TTL 300 s, single use).
- Tenant = `uuid5(server namespace, upstream subject)` (ADR 0005); the namespace is
  unique per server (regenerated by the scaffold), so two servers never share tenant ids.
- Access token: an 8 h ES256 JWT (iss/aud/exp verified locally). Refresh token: opaque,
  30 days, stored only as SHA-256 and rotated on every use.
- Every client is public (`token_endpoint_auth_method=none`) and PKCE S256 is mandatory.

## Consequences

- One login connects both the MCP client and the upstream account.
- A non-active tenant (ADR 0005) can neither log in again nor refresh; its current JWT
  lapses within 8 h.
- Changing the upstream provider does not change the OAuth contract the MCP client sees.
